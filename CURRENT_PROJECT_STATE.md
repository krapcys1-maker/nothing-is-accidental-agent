## Aktualne blokery

Brak blockerów Etapu 0 — kryterium zakończenia spełnione. Etap 1 ma trwały claim, active-topic lock, rezerwację, runtime PolicyEngine, minimalny worker, okresowy daemon guard heartbeat na osobnym połączeniu SQLite, jawny reaper `runs.status=RUNNING→STOPPED`, maintenance one-shot/poll oraz centralne, deterministyczne planowanie okien redakcyjnych przed enqueue, wszystko zweryfikowane offline. `SchedulingPolicy` wymaga jawnego `editorial_schedule`, waliduje IANA timezone/okna/DST, odrzuca czas przeszły, zapisuje UTC `earliest_run_at` i kontrolowany `schedule_reason`; worker nie claimuje joba przyszłego, nie tworzy lease i nie zwiększa attempts. Nie jest to usługa schedulera systemowego ani realny dispatch: końcowa akceptacja restartu pozostaje NOT_STARTED. Maintenance zawsze otwiera osobne SQLite, robi recovery jobów przed reaperem, zamyka połączenie i zatrzymuje poll przy błędzie; nie claimuje jobów, nie dispatchuje, nie uruchamia researchu i działa także przy wyłączonych flagach workera. Daemon jest wyłącznie ostatnią osłoną procesu: worker zawsze ustawia stop event, wywołuje `wake`, wykonuje bounded join i sprawdza `is_alive()`; timeout blokuje `DONE`, a później odblokowany guard widzi stop event przed kolejnym heartbeat. `lost_lease` i `failure` pozostają wyłącznie in-memory, zaś trwałe rozstrzygnięcie joba należy do SQLite oraz recovery/reconciliation. Guard nie robi retry dispatchu; utrata lease albo błąd guarda blokuje DONE, a utrata lease ma pierwszeństwo przed błędem dispatchu. Reaper najpierw wymaga recovery joba; powiązany RESEARCH pozostaje `NEEDS_VERIFICATION`, a run nigdy nie jest automatycznie wznawiany. Przed każdym płatnym albo browser/public workerem pozostają osobne granice bezpieczeństwa i zgoda właściciela; oba typy są teraz BLOCKED. Karta #2 ma `publication_recommendation=REJECT`, więc nie może zasilić przyszłego content pipeline bez poprawy dowodów. Historyczny run `9bbeb020` i P2-20 pozostają długiem technicznym.
